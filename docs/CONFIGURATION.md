# Модель, резюме и карта компетенций

Все настройки — в `hh-data/config.server.toml`. Новая инициализация хранит ключи в `hh-data/.env`; корневой `.env` и окружение контейнера также поддерживаются. Не сохраняйте личные конфиги, сессии, резюме и профили в Git.

## Инициализация из своих файлов

```bash
python scripts/configure.py init --gender male --provider openai --model YOUR_MODEL --profile "/path/to/my-profile.json" --competency-map "/path/to/my-cases.md"
```

Принимаются JSON и TOML-профили, Markdown-карта — дополнительный флаг. Для другого поставщика укажите `--provider custom --base-url https://your-provider.example/v1 --model your-model`; для женского рода — `--gender female`. Файлы копируются в `data/candidate_profile.json` или `.toml` и `data/competency_map.md` относительно созданного конфига. Можно использовать другой каталог: `--data-dir /path/to/my-data`.

Движок задаётся флагом `--browser-backend playwright` (по умолчанию) или `--browser-backend seleniumbase_uc`. UC предназначен для Linux с полным Chrome и Xvfb, которые включены в общий Docker-образ. Флаг только сохраняет выбор: `init` не скачивает и не запускает браузер.

`--resume` принимает ID или ссылку `https://hh.ru/resume/ID`, `--query` задаёт текст поиска. Ручной ID не подтверждает принадлежность аккаунту: после входа выполните `resumes list` и `resumes select --id ID`.

Без `--profile` дополнительный профиль не подключается. `init` ничего не генерирует, не обращается в hh и оставляет автоматические задачи выключенными. Все входные файлы проверяются до создания назначений. Существующие назначения защищены; `--overwrite` явно пересоздаёт конфиг и выбранные копии, сохраняя файл ключей. Для действующей установки обычно достаточно изменить нужные поля и проверить их через `doctor`.

```bash
python scripts/configure.py doctor --data-dir /path/to/my-data
python scripts/configure.py doctor --config /path/to/my-data/config.server.toml --data-dir /path/to/my-data --env-file /path/to/my-data/.env --json
```

Doctor не меняет файлы и окружение процесса, не открывает браузер, не вызывает модель, не печатает ключи, cookies, тексты резюме или фактов. Возвращает код `2`, если остаются обязательные шаги. Проверка сессии здесь локальная; фактический вход проверяет `session check`. При старом корневом `.env` явно задайте `--env-file .env` для локального doctor.

## Интервалы и ограничения запросов

Новая инициализация берёт эти значения из публичного серверного шаблона. Автозадачи при этом остаются выключенными:

```toml
[limits]
max_responses = 10
submission_interval_seconds = 180
submission_batch_size = 2
submission_batch_pause_minutes = 25
captcha_cooldown_minutes = 120
read_interval_seconds = 10
max_responses_per_day = 10
captcha_rest = 0

[watch]
robot_replies = false
robot_every_minutes = 15
robot_max_chats_per_check = 10
robot_reply_interval_seconds = 30
```

`submission_interval_seconds` задаёт минимальный интервал попыток отправки откликов. После `submission_batch_size` попыток действует `submission_batch_pause_minutes`; при включённом размере серии пауза должна быть положительной. Попытка резервируется перед необратимым действием; ошибка отправки не возвращает место в серии. На обычной паузе сервер закрывает браузер и продолжает задачу позже, сохраняя возможность проверять роботов. `read_interval_seconds` ограничивает частоту чтения страниц.

`max_responses` ограничивает один запуск, `max_responses_per_day` — дневную квоту за текущую дату `Europe/Moscow`. В неё входят подтверждённые отклики в общей истории программы и сегодняшние попытки с ещё неясной доставкой: неопределённость не освобождает место для новой отправки. Ручные CLI-запуски и технические повторы используют ту же квоту, если записаны в общую историю. Отклики, сделанные самостоятельно на сайте и не записанные программой, этот счётчик не знает.

Первая обнаруженная CAPTCHA сохраняет общий срок паузы на `captcha_cooldown_minutes`: до его окончания приостанавливаются все фоновые запросы к hh, включая роботов и технические повторы. Перезапуск контейнера не отменяет эту паузу. Программа не ждёт ручного решения CAPTCHA и не повторяет отправку сразу после её появления. Снижение частоты запросов не гарантирует отсутствия CAPTCHA.

`robot_every_minutes` — интервал после окончания предыдущей проверки. Полный список чатов с последним сообщением за 30 дней пополняет сохраняемую очередь, но за цикл открывается не больше `robot_max_chats_per_check`. До 40% мест получают новые, непрочитанные или изменившиеся чаты; остальные идут по очереди FIFO. Прочитанные чаты тоже проверяются. При большой очереди отдельный чат может ждать несколько циклов: 15 минут не являются гарантированным сроком ответа. `robot_reply_interval_seconds` задаёт минимальный интервал отправок ответов.

У шести новых полей `[limits]`, а также `robot_max_chats_per_check` и `robot_reply_interval_seconds`, значение `0` отключает соответствующее ограничение для совместимости со старыми конфигами. При включённых роботах `robot_every_minutes` должен быть не меньше 1. Старый адаптивный `captcha_rest` предназначен для конфигов без новой политики отправок; при включении новой политики программа отключает его, чтобы два таймера не складывались.

После изменения перезапустите сервис. `configure doctor --json` возвращает настроенные числовые значения в `request_timing.limits` и `request_timing.watch`; обычный вывод показывает те же интервалы с единицами. Doctor не читает текущие задания или сроки пауз. Фактическую причину отсрочки и срок возобновления проверяйте через `server --status`.

Сроки ограничений хранятся в `data/submission-pacing.json`, очередь обхода чатов — в `data/robot-chat-scan.json`. Сохраняйте их вместе с остальной историей при переносе и обновлении.

## Браузерный движок

```toml
[browser]
backend = "playwright"  # альтернативный движок: seleniumbase_uc
headless = true
channel = ""
```

`playwright` использует Chromium Playwright. `seleniumbase_uc` на Linux при `headless = true` запускает полный Chrome на внутреннем виртуальном экране Xvfb; видимого окна или VNC нет. Для UC допустимы пустой `channel` и `"chrome"`; Edge не поддерживается. Невидимый UC на Windows не запускается: локальный вход и выбор резюме подготовьте через Playwright, затем переключите движок в Linux-конфиге.

Doctor возвращает `browser_backend` в JSON и отдельную строку проверки движка. Это метаданные настроек, а не проверка установленного Chrome/Xvfb или входа в hh. При смене движка достаточно правки `[browser] backend` и перезапуска: настройки модели, род, выбранное резюме и личные файлы не меняются. UC хранит браузерное состояние отдельно и использует переносимый файл сессии при создании нового профиля. Проверки и возврат к Playwright описаны в [SERVER_RU.md](../SERVER_RU.md#выбрать-браузерный-движок). Обход CAPTCHA или отсутствие блокировок не гарантируются.

## Выбор модели

Для OpenAI:

```toml
[ai]
enabled = true
provider = "openai"
model = "ИМЯ_ДОСТУПНОЙ_ВАМ_МОДЕЛИ"
api_key = ""
only_robot = true
```

В `.env` задайте `OPENAI_API_KEY`. Имя модели должно быть доступно вашему API-проекту. Смена имени не меняет фильтры и расписание.

Для другого OpenAI-совместимого поставщика:

```toml
[ai]
enabled = true
provider = "custom"
base_url = "https://your-provider.example/v1"
model = "your-model-name"
api_key = ""
only_robot = true
```

В `.env` используйте `HH_AI_API_KEY`. `base_url` — корень API, без `/chat/completions`: клиент добавляет путь сам. API должен поддерживать используемые проектом Chat Completions и ответы в JSON. `HH_AI_API_KEY` имеет приоритет над `OPENAI_API_KEY`, поэтому не оставляйте одновременно старый ключ другого поставщика.

Для Ollama задайте `provider = "ollama"`, адрес и установленное имя модели. В контейнере `localhost` означает сам контейнер, поэтому удалённой Ollama нужен адрес, доступный с сервера. Подробности — [ollama.md](ollama.md). Проверка генерации:

```bash
docker compose -f docker/docker-compose.yml stop hh
docker compose -f docker/docker-compose.yml run --rm hh python /app/scripts/ai_test.py --config /data/config.server.toml --letter
```

Команда вызывает модель, но не отправляет письмо в hh. Не используйте `--show-prompt`/`--raw` в общедоступных логах: там могут быть факты профиля и резюме.

## Род кандидата в письмах и ответах

В `[ai]` задайте `candidate_gender` независимо от модели и профиля:

```toml
[ai]
candidate_gender = "male"  # мужской род; female — женский
```

`male` даёт формы «работал», «реализовал», «готов»; `female` — «работала», «реализовала», «готова». В выходном тексте используется один выбранный род, без форм «работал(а)». Допустимы только `male` и `female`; при отсутствии поля применяется `male` для совместимости со старыми конфигами. После изменения перезапустите сервис.

## Выбранное резюме

`resumes list` читает собственные резюме из аккаунта. `resumes select --id ID` привязывает конфиг к одному ID и сохраняет остальные фильтры. `resumes fetch` обновляет `data/resume.txt` и `data/resume.txt.id`.

Резюме, по которому идут отклики, служит источником фактов для писем. Кэш другого ID не подставляется. Профиль компетенций дополняет резюме; это отдельный файл, который удобно обновлять без правок программы.

## Простой TOML-профиль

Скопируйте `candidate_profile.example.toml` в `hh-data/data/candidate_profile.toml`, замените синтетический пример своими фактами и включите:

```toml
[ai]
profile_path = "data/candidate_profile.toml"
```

В профиле указываются `role`, `confirmed_skills`, `clarifications` и список `[[projects]]` с названием, технологиями и личными задачами. Общий список навыков не означает автоматически, что каждая технология использовалась в каждом проекте.

## JSON-профиль с уровнями подтверждения

Расширенный пример — `candidate_profile.example.json`. Скопируйте его в `hh-data/data/candidate_profile.json` и заполните:

- `candidate` — роль, актуальные сведения и только подтверждённые общие утверждения о стаже.
- `competencies` — категории с уровнями `hands_on`, `familiar`, `needs_confirmation`.
- `projects` — конкретные кейсы, `technology`, `personal_contribution`, ограничения стадии и вклада.
- `screening_examples` — при необходимости собственные подтверждённые примеры ответов.

```toml
[ai]
profile_path = "data/candidate_profile.json"
```

`hands_on` — личная практическая работа; `familiar` — знакомство; `needs_confirmation` — факт пока не подтверждён. Стек команды не равен вашему личному опыту со всеми компонентами. Общий стаж нельзя приписывать каждому фреймворку. Не добавляйте неподтверждённые метрики, клиентов, ссылки, NDA или production-опыт.

Пустой `profile_path` отключает дополнение. Если непустой путь неверен или профиль повреждён, программа выдаёт ошибку вместо молчаливого игнорирования файла.

## Дополнительная карта кейсов

Скопируйте `competency_map.example.md` в `hh-data/data/competency_map.md`. Каждый кейс начинается с нумерованного заголовка третьего уровня:

```markdown
### 1. Точное название проекта из профиля

Личная задача, применённые инструменты, стадия результата и ограничения.
```

Название после номера должно совпадать с `projects[].name`. Только соответствующий раздел добавляется к конкретному проекту; общие указания вокруг разделов не используются как доказательства опыта.

```toml
[ai]
profile_path = "data/candidate_profile.json"
competency_map_path = "data/competency_map.md"
profile_notes_path = ""
```

Все три пути отсчитываются от папки конфига. В Docker `/data/config.server.toml` и `data/candidate_profile.json` означают файл `/data/data/candidate_profile.json`. Перенесите оба файла на сервер вместе с личными настройками. Обновление профиля применяется при следующем создании AI-клиента; после правки перезапустите сервис.

## Свои предпочтения

Краткие личные факты и условия можно добавить в `[ai] context`. `answer_prompt` задаёт стиль ответов, `[letter] ai_prompt` — дополнительные пожелания к письмам. Инструкции вакансии, например обязательные вопросы в начале или английский язык, обрабатываются отдельно.

Сами фильтры не задаются текстом профиля: используйте `[hh_filters]` и `[filters]` в конфиге. Для слов, которые исключают вакансию по содержанию, используйте `exclude_description_words`; для названия — `exclude_title_words`. Проверяйте результат через `responses --dry-run`.
